# 『帰り唄 ―手毬唄の館―』体験・テンポ・UI評価

評価日: 2026-07-28。コード／シナリオは変更せず、静的読解と `tools/AIプレイ/ログ` の11通しプレイを根拠にした評価である。

## 1. 総評

一周の物語体験は、倒叙の緊張を保つ情報提示と「行動には代償がある」自由行動がよく噛み合っている。通常テキスト、選択、特殊パートが交互に来るため、長めの本文でも単調にはなりにくい。既読スキップ、章頭スナップショット、END回想も揃っており、周回を前提とするADVとしての土台は強い。

ただし初見者には、自由行動の「何を取れば後段の条件を満たせるか」と、共同推理の「どのカードがなぜ必要か」の接続が見えにくい。初心者ログはB-1へ到達しているが、最終推理では安全そうな「コウナンに任せる」を連続選択しており、システムの意図を理解して能動的に解いた結果とは言いにくい（`tools/AIプレイ/ログ/shoshinsha.md:4073-4093`）。また本文送りはAIログ上で非常に多い。ログは文字送り途中も1ステップとしているため700回超を700クリックとは数えられないが、「一つの本文ノードで最大二操作（全文表示、次ノードへ）」になり得る設計は、未読の初周で明確な反復負荷である（`src/ui/message-window.js:47-53`, `src/main.js:254-262`）。

結論として、初周は**65〜80分の密度ある中編ADVとして適正**、全END収集は実装上かなり短縮できる一方、初見の「情報の意味づけ」とキーボード時の特殊パート導線に改善余地がある。

## 2. 定量データ

再現用に実行したスクリプトは以下である（`/tmp/count-scenario.mjs` に置き、リポジトリ直下で `node --experimental-default-type=module /tmp/count-scenario.mjs` を実行後に削除した）。`Array.from` によりサロゲートペアも1字として数える。

```js
import { pathToFileURL } from 'node:url';

const load = (name) => import(pathToFileURL(`${process.cwd()}/src/data/scenario/${name}.js`));
const { prologue } = await load('prologue');
const { chapter1 } = await load('chapter1');
const { chapter2 } = await load('chapter2');
const { chapter3 } = await load('chapter3');
const { chapter4a } = await load('chapter4a');
const { chapter4b } = await load('chapter4b');
const { endings } = await load('endings');

const scenes = [prologue, chapter1, chapter2, chapter3, chapter4a, chapter4b,
  ...Object.values(endings)];
const rows = [];
function walk(value, scene) {
  if (!value || typeof value !== 'object') return;
  if (Array.isArray(value)) return value.forEach((v) => walk(v, scene));
  if (['say', 'mono', 'stage'].includes(value.t) && typeof value.text === 'string') {
    rows.push({ scene: scene.id, text: value.text });
  }
  Object.values(value).forEach((v) => walk(v, scene));
}
scenes.forEach((scene) => walk(scene.nodes, scene));
for (const scene of scenes) {
  const own = rows.filter((r) => r.scene === scene.id);
  console.log(scene.id, own.reduce((n, r) => n + Array.from(r.text).length, 0));
}
console.log('TOTAL', rows.reduce((n, r) => n + Array.from(r.text).length, 0));
```

一周で通る本文は、選ばない自由行動・分岐・未到達ENDを除くため概ね2.8〜3.2万字と見積もる。500字/分で56〜64分、選択37回と特殊パートの考慮7〜15分を加え、**標準65〜80分**とした。じっくり推理・手帳確認では80〜100分、既読スキップ周回は下記の通り大幅に短い。これは長すぎず、倒叙ミステリーの情報量に見合う。ただし初周の「全文を出す→送る」が多いことはテンポを鈍らせる。

### AIプレイログの手数

11ペルソナの完走ログを、各Markdown見出し `## n. … — advance / choice / part` で集計した。合計8,765、平均 **796.8ステップ**（最少659、最多854、中央値820）。内訳平均は **advance 704.9、choice 37.0、part 54.9**。END対応は suiri=B-1、bannin=A-1、kanjou=B-1、sokkyou=A-1、ura=A-3、toubou=A-2、ayatsuri=A-1、gyakuten=A-4、mikiri=B-3、shoshinsha=B-1、danzai=B-2 で、指定された対応と一致する（`tools/AIプレイ/ログ/サマリ.json`）。

重要なのは、`advance` は実クリック数ではないことだ。ログはタイプライター途中の画面と全文表示後の画面を別ステップに記録する。実装も表示中の送りを「全文表示」、表示完了後の送りを「次ノードへ」に分けている（`src/ui/message-window.js:47-53`）。従って本文ノードの操作負荷はおおむね **1〜2回/ノード**、ログのadvance平均704.9はその上限寄りの観測値である。37の選択と約55の特殊パート操作は、二重記録ではない実質的な意思決定／UI操作として残る。

### 215字超のメッセージノード検査

`say` / `mono` / `stage` の各 `text` を上記スクリプトと同じ再帰走査で `Array.from(text).length > 215` として機械検査した結果は **0件**。従って「215字超のノード一覧」は**該当なし**である。最大表示域は4行固定でスクロール可能（`src/styles/main.css:60-70`）、表示完了時は最下端へ自動スクロールする（`src/ui/message-window.js:22-29`）ため、今後215字を越えると冒頭を見失わせやすい。現データはこの制約を守れている。

## 3. 周回性の評価

全ENDを見るために必要な到達回数は、A-1〜A-4、B-1〜B-3の **7回**である。回想モードはクリア済みENDを再読する機能で、未解放ENDへ飛ぶ機能ではない（`src/ui/gallery.js:45-67`）。したがって条件確認を含む完全収集は原則7到達が必要である。

ただし「7回すべてを初周時間でやる」必要はない。

|手段|実効性|限界|
|---|---|---|
|既読のみスキップ|既読ノードは16〜30ms間隔で自動送り。本文の再読をほぼ除ける（`src/engine/playback.js:45-56`）|選択・特殊パート・未読分岐で停止する（同:38-43）。既読情報はノード単位で保存される（`src/engine/progress.js:119-145`）。|
|未読もスキップ|設定で全ノードをスキップ可能（`src/ui/settings.js:6-8`, `src/engine/playback.js:31-33`）|初見分岐を飛ばす危険があり、選択／特殊パート前では止まる。|
|章選択|章遷移ごとに専用スロットへ自動保存し、到達済み章をタイトルから再開できる（`src/main.js:60-71`, `src/main.js:386-390`, `src/data/chapters.js:18-28`）|分岐直前ではなく章頭へ戻る。章内の取り逃しは回収できない。|
|3枠＋オートセーブ|第四章の分岐前に手動セーブすればA系、B系の枝を即座に試せる。END時にもオート保存（`src/engine/save.js:4-7`, `src/main.js:506-524`）|特殊パート中の保存はパート開始へ戻る仕様（`src/main.js:300-314`）。|
|回想モード|取得済みENDはタイトルから直接再読（`src/ui/gallery.js:55-63`）|未取得ENDの解放・条件表示はしない。|

最短の実務的な収集は、初周を約70分、以後は章選択＋既読スキップで必要な自由行動／第四章のみを再操作する形になる。A-1〜A-4とB-1〜B-3を分岐直前セーブでまとめれば、残り6到達は各10〜20分程度、**全7ENDは約2〜3時間**が目安である（初周の取得状態・セーブ位置に依存）。全ルートをスキップなしで読むなら7×65〜80分＝**7時間35分〜9時間20分**。周回は苦行ではないが、END条件をゲーム内で振り返れないため、収集者は外部メモか試行錯誤を要する。

## 4. 改善点

### 優先度: 高

#### H-1 自由行動と最終条件の因果を、ゲーム内で追えるようにする

1. 問題: 自由行動では報酬・代償の事前ヒントをオンにできるが、取得した情報が「どの後段の反論・共同推理に使えるか」は手帳に出ない。初心者は安全そうな対人行動を選び、条件に関わる探索を落としうる。
2. 根拠: ヒントは設定で初期オフ（`src/engine/progress.js:5-14`, `src/ui/settings.js:3-12`）。自由行動画面は残ブロックと取得済み行動を示すのみ（`src/systems/freeaction/index.js:196-216`）。手帳は証言、未取得を `?` とするフラグ、カード名・説明を並べるが、用途／未達の推理ノードは示さない（`src/systems/notebook/index.js:58-101`）。初心者はstep 222で「家政婦と話す」を安全性で選び、その後の共同推理では代理を多用した（`tools/AIプレイ/ログ/shoshinsha.md:4031-4033`, `4073-4093`）。
3. 具体案: 初見時は事前ヒントを既定オンにする。手帳のカードに「使える局面: 反論／共同推理」「未確認の関連: ？」を、ネタバレ段階に応じて表示する。章末サマリには未取得行動名だけでなく、次章で重要になり得る情報カテゴリを一文で示す。
4. 副作用: 条件の可視化が強すぎると推理の手触りと倒叙の不安が薄れる。表示は「使える可能性がある」までに留め、正解ノード名・必要数は隠すべきである。

#### H-2 特殊パートの初回説明と失敗時の学習を補う

1. 問題: 反論、手毬唄ボード、共同推理は操作できるが、初見で「何を最適化するのか」「空欄／代理選択の結果」が一画面で理解しにくい。
2. 根拠: 反論データには設計意図があるが画面へ出す処理はない（`src/data/parts/rebuttal-ch2.js:1-16`）。ボードは二面・3スロット・三つのスコアを初期から提示する（`src/systems/temariuta-board/index.js:54-65`）。共同推理はカード条件を明示せず、使える「自分で暴く」をdisabledにするだけで、代理が常に有効なノードもある（`src/systems/inference/index.js:5-10`）。初心者ログはボードの操作表示を14ステップ連続で経由（`tools/AIプレイ/ログ/shoshinsha.md:2045-2136`）、最終推理で「コウナンに任せる」を多数選択した（同:4073-4077）。
3. 具体案: 各パート初回のみ閉じられる3行チュートリアルを出す。反論は「カード＝反証、沈黙＝数値を守らない場合がある」、ボードは「札→欄→確定、二面の違い」、共同推理はdisabled理由を「必要な手掛かりが不足」としてカード名を伏せて表示する。失敗／代理後にも次回へ効く短いフィードバックを残す。
4. 副作用: モーダルと説明文が増え、既読者のテンポを損なう。初回限定、または設定で再表示可能にする。

### 優先度: 中

#### M-1 本文送りの二段階負荷を緩和する

1. 問題: 長い初周では、本文表示を完了する操作と次へ進む操作が分離される。AIログの平均advance 704.9は二重記録込みだが、本文の操作密度が高いことを示す。
2. 根拠: 表示中の入力は全文表示、表示後だけ進行する（`src/ui/message-window.js:47-53`, `src/main.js:254-262`）。11ログの本文送りは合計7,754／平均704.9、全ステップの88.5%である（`tools/AIプレイ/ログ/*.md` の見出し集計）。
3. 具体案: 設定に「クリックで即時送り（全文表示と次送りを統合）」を追加するか、短文ではタイプライターを省略する。現行のテキスト速度・オート・スキップは維持する。
4. 副作用: 誤クリックで台詞を読み飛ばしやすい。統合は明示設定にし、既定は現行の安全な二段階のままとする。

#### M-2 END収集の次の一手を示す

1. 問題: 回想モードはクリア済みENDと件数のみを示し、未取得ENDは `???` で、分岐を探す復帰導線がない。
2. 根拠: 未クリアカードは「ロック中」、再読ボタンはクリア済みだけに付く（`src/ui/gallery.js:45-67`）。END時の説明は次のヒントを生成しているが、全ENDの条件一覧にはならない（`src/main.js:515-524`）。
3. 具体案: 回想カードにネタバレ段階別のヒント（例: 「第四章Aの別の態度」「自由行動で📜を増やす」）と、直近章頭セーブへの「ここから再開」を表示する。
4. 副作用: 完全な条件表示は探索性を削ぐ。ヒントは一段ずつ解放し、正解選択肢名は出さない。

#### M-3 バックログ／手帳へのキーボード発見性を補う

1. 問題: キーボード機能は実装されているが、バックログは上ホイールまたはHUDクリック、手帳はNまたはHUDクリックで、ゲーム内の常時表示からはショートカットが分かりにくい。
2. 根拠: キー割当は `Space/Enter/Ctrl/S/A/L/N/Esc`（`src/main.js:113-161`）、HUDの可視文言は「手帳」「ログ」だけ（`src/ui/hud.js:1-10`）。
3. 具体案: HUDボタンの `title` と画面設定にショートカット一覧を常設し、手帳・ログのボタンを「手帳 [N]」「ログ [↑ホイール]」と表示する。
4. 副作用: 1280×720のHUDが窮屈になる。ツールチップと設定内一覧を主にし、狭幅では短い表記に留める。

### 優先度: 低

#### L-1 手帳の未取得表示を「不足」ではなく探索可能な手掛かりへ変える

1. 問題: フラグ手帳の `?` は未取得事実だけを示し、どこで探すかは分からない。
2. 根拠: 全フラグ定義を走査して所持／`?` を列挙する実装（`src/systems/notebook/index.js:67-75`）。
3. 具体案: 一度遭遇した関連人物・部屋がある場合だけ、`?` に「館内で得られる手掛かり」のような弱い分類を付ける。
4. 副作用: 未発見内容の存在を早期に知らせる。初見では分類非表示、周回またはヒントONで表示する。

#### L-2 長文制約の自動検査を継続CI化する

1. 問題: 現在は215字超0件だが、4行固定＋最下端スクロールのため、将来の一本の長文追加で可読性を損なう。
2. 根拠: 表示域4行（`src/styles/main.css:60-70`）、全文表示時に最下部へ移動（`src/ui/message-window.js:22-29`）、今回の機械検査は0件。
3. 具体案: シナリオ検証に `say` / `mono` / `stage` の215字上限チェックを加え、超過時は `file:line` を標準出力する。
4. 副作用: 演出上どうしても長文にしたい場面が止まる。明示的な例外フラグを設ける。

### アクセシビリティ所見

通常進行はSpace/Enter、選択は矢印・数字・Enterで操作できる（`src/main.js:129-149`, `src/ui/choice.js:56-71`）。HUD、セーブ、設定、手帳、バックログの主要操作はbuttonであり、手帳／ログは開いた際に閉じるボタンへフォーカスする（`src/systems/notebook/index.js:106-127`, `src/ui/backlog.js:60-82`）。特殊パートも主要選択はbuttonで、ボードの面切替にはEnter/Spaceがある（`src/systems/temariuta-board/index.js:61-66`）。したがって**Tab/Shift+Tab、Enter/Space、矢印、数字、既定ショートカットを使えば、ポインタなしで最後まで進める設計**である。

ただし完全なフォーカストラップは設定・セーブ等で確認できず、ショートカットの画面内説明も薄い。キーボード専用利用者には、上記M-3と、各モーダルのフォーカス循環／Esc案内を追加すると確実性が上がる。
